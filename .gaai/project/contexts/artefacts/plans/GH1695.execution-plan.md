# GH1695 Execution Plan: contracts.py Distribution and Import Standardization

## Summary

The `contracts.py` and `cors.py` modules in `src/shared/python/` are bare Python files
(not packages). The `[tool.setuptools.packages.find]` directive only discovers packages
(directories with `__init__.py`), so these modules are omitted from `pip install ud-tools`.
This makes the `contracts`/`cors` import chain fragile in package distributions.

Additionally, 10+ `src/` files and several `tests/` files use the CWD-dependent absolute
path `from src.shared.python.contracts import ...` instead of the short form
`from contracts import ...` which works when `src/shared/python` is on `sys.path`.

## Approach

1. **Fix package distribution** — Add `contracts` and `cors` to `[tool.setuptools.py-modules]`
   in `pyproject.toml` so they are included in `pip install ud-tools`.

   Note: `pyproject.toml` with setuptools supports `[tool.setuptools]` -> `py-modules` as a list.
   Alternatively, use `packages.find` with explicit include of top-level modules. The cleanest
   approach is `[tool.setuptools]` → `py-modules = ["contracts", "cors", ...]`.

2. **Standardize imports in `src/` files** — Convert 10 `src/` files (non-test) from
   `from src.shared.python.contracts import ...` to `from contracts import ...`.
   This stays within the AC scope (fixing the fragile import chain).

3. **Do NOT change test files** — The test files using `from src.shared.python.contracts import`
   also work (since `src` is on pythonpath). Changing ~40 test file locations is beyond the
   story scope and is a separate cleanup story.

4. **Add/update tests** for the distribution fix, specifically:
   - A test verifying `contracts` and `cors` can be imported with short-form imports
   - Tests already exist in `tests/shared/python/test_cors.py` and `test_contracts.py`

## File-Level Steps

### Step 1: Fix pyproject.toml — add py-modules

**File:** `pyproject.toml`

Add under `[tool.setuptools]`:
```toml
[tool.setuptools]
py-modules = ["contracts", "cors", "deprecation", "safe_eval"]
```

This tells setuptools to include bare `contracts.py`, `cors.py`, `deprecation.py`, `safe_eval.py`
from the `src/shared/python` directory (since it's listed in `where`).

Wait — the `py-modules` directive with `find` doesn't combine cleanly. The correct approach
with setuptools is to use `[tool.setuptools]` top-level `py-modules` which requires specifying
the root directory. Since `src/shared/python` is in `where`, but `py-modules` is top-level,
we need to verify this works correctly.

**Better approach:** Use `[tool.setuptools.packages.find]` with `include` list extended to
also cover these modules via a wildcard, OR explicitly use `package-dir` mapping.

**Cleanest approach:** Since `src/shared/python` is already in `where = [...]`, adding
`[tool.setuptools]` → `py-modules = ["contracts", "cors", "deprecation", "safe_eval"]`
should pick up these modules from the search path roots.

## Edge Cases

- `src/tools/ui_utils.py`, `dependency_utils.py`, `config_loader.py` use `try/except ImportError`
  guards for `contracts` — update only the absolute-path fallback branch inside those guards
- `src/data_processing/data_processor/python/data_processor/contracts.py` uses a try/except
  with `from src.shared.python.contracts import ...` fallback — this is a subproject with a
  different path setup; leave it unchanged to avoid unexpected breakage
- `pyproject.toml`'s `py-modules` must list modules relative to the `where` directory

## Risk Register

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| `py-modules` with `where` behaves unexpectedly in setuptools | Low | Test import after edit |
| Changing conditional imports breaks fallback logic | Low | Only update the absolute path, preserve try/except structure |
| Ruff catches style issues in modified files | Very low | Run ruff after each file change |

## Rollback Boundary

If `pyproject.toml` `py-modules` causes issues, revert that specific section only.
The import standardization changes are independently safe.
