# GH1691 Execution Plan: Refactor Long Functions (>100 lines)

## Summary

15 functions exceed 100 lines. This plan extracts helper functions from the top
offenders where the length reflects genuine complexity (not docstring bulk), reducing
function bodies to <100 lines while leaving public API signatures unchanged.

## Complexity Assessment

**Tier 2** — 6 files, algorithmic + UI refactoring, TDD requirements.

## Approach Evaluation

No non-obvious choices. The approach follows the established convention from GH1650
(extract private helpers, keep public signature unchanged, add tests for new helpers).
No approach evaluation artefact needed.

## Pre-Analysis: Which Functions to Refactor

Functions were analysed for the source of their length:

due to extremely verbose docstrings containing matrix-formatted example code. The actual
logic is 34L and 53L respectively. Touching these risks introducing docstring formatting
errors with no quality benefit. They are excluded from this plan.

## File-Level Steps

### Step 1: `src/pendulum_simulator/src/double_pendulum_golf/gui/panel_builders.py`

**Target functions**: `build_double_panel` (179L), `build_triple_panel` (197L),
`build_golfer_panel` (239L), `wire_toolstrip` (143L)

**Pattern**: All three `build_*` functions follow the same structure:
1. Widget creation (small closures: build_params, build_state, etc.)
2. Optimizer widget creation
3. Objective builder closure
4. Panel creation
5. Perturbation panel wiring (~40-50 lines each)

**Extraction**:
- Extract the perturbation-panel wiring block from `build_double_panel` into a module-level
  private function `_wire_double_perturbation(panel, controls, build_params, build_state,
  build_limits, build_clamp)` → returns the configured `PerturbationPanel`.
- Extract the same from `build_triple_panel` → `_wire_triple_perturbation(...)`.
- Extract the same from `build_golfer_panel` → `_wire_golfer_perturbation(...)`.
- Extract from `wire_toolstrip`: split the signal-connection loops into
  `_wire_panel_signals(ts, panel)` private helper.

After extraction, `build_double_panel` target: ~120L, `build_triple_panel`: ~130L,
`build_golfer_panel`: ~165L, `wire_toolstrip`: ~95L.

Note: `build_golfer_panel` will still be ~165L after extraction due to its 7-DOF
parameter builder closure. This is acceptable — the function's complexity is inherent
to the 7-DOF golfer model. Further extraction would not improve readability.

### Step 2: `src/shared/python/programmatic_pid/cli.py`

**Target functions**: `generate_process_sheet` (188L), `generate_controls_sheet` (237L)

**`generate_process_sheet` phases**:
1. Doc setup + layer resolution + layout config (~35L)
2. Title/subtitle text + border boxes (~30L)
3. Equipment + instruments + streams + control loops rendering (~80L)
4. Notes + footer text + save/export (~20L)

**Extraction**:
- Extract phase 1 into `_setup_process_doc(spec) -> tuple[doc, msp, t, layout_regions, layer_names]`
  — returns the configured document context.
- Extract phase 3 (equipment/instrument/stream rendering) into
  `_render_process_elements(msp, spec, t, layers, layout_regions)` — void, draws directly.

After extraction, `generate_process_sheet` target: ~90L.

**`generate_controls_sheet` phases**:
1. Doc setup + layer resolution + dimensions (~35L)
2. Header text + table structure + control loop rows (~120L)
3. Interlock/instrument lower panels + save/export (~30L)

**Extraction**:
- Extract phase 2 (table header + loop rows) into
  `_render_controls_table(msp, spec, t, layout_cfg, x_min, y_min, x_max, y_max, layers)`.

After extraction, `generate_controls_sheet` target: ~90L.

### Step 3: `src/pendulum_simulator/src/double_pendulum_golf/gui/toolstrip_widget.py`

**Target functions**: `_build_row1` (166L), `_build_overlay_section` (228L)

**`_build_row1` sections**:

After extraction, `_build_row1` target: ~85L.

**`_build_overlay_section` sections**:

**Extraction**:

After extraction, `_build_overlay_section` target: ~130L.
(Still >100L but significantly reduced. The overlay frame with 3 rows is inherently dense.)

### Step 4: `src/rotation_converter/modern_robotics.py`

**Target function**: `SimulateControl` (224L)

The actual logic is lines 2001–2084 (~83L). The function body length is dominated
by the docstring (119L).

The plotting block (lines 2047–2081, ~35L) is self-contained and side-effect-only.

**Extraction**:
- Extract the matplotlib plotting block into module-level private function
  `_simulate_control_plot(thetamat, thetamatd, dt)` — same logic, no return value.
- `SimulateControl` calls `_simulate_control_plot(thetamat, thetamatd, dt)` in place
  of the try/except/import block.

After extraction, `SimulateControl` body logic: ~50L. Total function (with docstring): ~170L.
(The docstring cannot be shortened — it is part of the published modern_robotics API.)

### Step 5: `src/pendulum_simulator/src/double_pendulum_golf/physics_golfer_jax.py`

**Target functions**: `analytical_fk_jacobians_jax` (181L), `forward_kinematics_jax` (114L)

**`analytical_fk_jacobians_jax`** computes position Jacobians for 7 body points.
Each body's Jacobian is ~20-25L of independent computation. The function is a
sequential accumulation into a `jacobians` dict.

**Extraction**:
- Extract the right-arm Jacobians (hub, rs, re, rh) into
  `_right_arm_jacobians(p, sin_hub, cos_hub, sin_rs, cos_rs, sin_re, cos_re) -> dict`.
- Extract the left-arm Jacobians (ls, lh) into
  `_left_arm_jacobians(p, sin_hub, cos_hub, sin_ls, cos_ls, sin_le, cos_le) -> dict`.
- Extract the club Jacobian into `_club_jacobian(p, ...) -> JaxArray`.

After extraction, `analytical_fk_jacobians_jax` target: ~65L.

**`forward_kinematics_jax` (114L)**: reads as sequential per-body position computation.
Similar pattern — extract `_right_arm_positions(q, p)` and `_left_arm_positions(q, p)`.

After extraction, `forward_kinematics_jax` target: ~65L.

## Edge Cases

- `SimulateControl` docstring is part of the published modern_robotics API. Do not
  shorten or reformat it. The function will still be >100L total due to docstring.
- Extracted JAX helpers must use `jnp.zeros` / `.at[].set()` patterns (no in-place ops).
  These helpers must be pure functions compatible with `jit` and `vmap`.
- Panel builder closures (`build_params`, `build_state`, etc.) capture variables from
  the outer scope. Extracted perturbation helpers must receive these closures as
  parameters — do not use class-level state.
- `_wire_double_perturbation` etc. must return the configured `PerturbationPanel` (not
  call `panel.set_perturbation_panel` internally — that stays in the public function).

## Risk Register

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| Panel builder closures capture outer scope; extracted helper breaks capture chain | Medium | Pass closures as explicit parameters to extracted helpers |
| JAX helpers not jit-compatible (side effects) | Low | Keep helpers as pure functions; use `.at[].set()` not in-place |
| `SimulateControl` still >100L after extraction (due to docstring) | Certain | Acceptable — logic is short; story asks to "extract helper functions" |
| `build_golfer_panel` still ~165L after extraction | Certain | Acceptable — 7-DOF model inherently requires more setup than 2-DOF double |
| DXF helper extraction changes rendering order | Low | Preserve sequential order; pass all needed context as parameters |
