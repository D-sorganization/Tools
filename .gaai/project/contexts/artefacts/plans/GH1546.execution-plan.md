# GH1546 Execution Plan: Add cross-repo Python consumer integration workflow

## Story Summary

Add a required GitHub Actions workflow that validates shared Python packages in `Tools` against downstream consumers (`Gasification_Model`, `UpstreamDrift`). Fail CI when changes break consumer contracts.

## Existing State

A `cross-repo-python-integration.yml` workflow already exists (added in #1552). It:
- Runs on push to `main` (not `staging`) and PRs matching `src/shared/python/**`
- Checks out both downstream repos and runs `tests/shared_contracts/` pytest suites
- Gracefully skips if downstream can't be checked out or suite doesn't exist

## Gap Analysis vs Acceptance Criteria

| AC | Gap | Severity |
|----|-----|----------|
| AC1: CI fails when Tools changes break downstream | Push trigger only on `main`, not `staging` | Medium |
| AC1: CI fails when Tools changes break downstream | `paths` filter too narrow — only `src/shared/python/**`, missing other shared paths | Low |
| AC2: Output identifies failing consumer + contract category | Summary shows downstream name but not test category breakdown | Low |
| AC3: Required for merges affecting shared packages | Workflow is standalone — not wired into `ci-standard.yml`; PR `paths` filter means it won't run as required check if no shared paths changed | Medium |

## Implementation Steps

### Step 1: Expand trigger paths in cross-repo-python-integration.yml

Add `staging` to push branches trigger. Expand `paths` to cover additional shared Python locations:
- `src/shared/python/**` (existing)
- `src/python/**` (shared python packages)
- `manifests/**` (manifest changes can affect consumer import paths)
- `.github/workflows/cross-repo-python-integration.yml` (existing)

### Step 2: Improve summary output to include contract category

In the "Summary" step, add contract category extraction from the test command output. Since this runs as a post-step summary, enhance it to note that pytest verbose output (already using `-v --tb=short`) shows contract categories from test file/class names.

Add explicit note in summary about what `tests/shared_contracts/` contains — this identifies the "contract category" as the test module name in the pytest output.

### Step 3: Ensure the PR trigger covers staging branch

Add `pull_request` trigger targeting `staging` branch merges (the default PR target in this repo):
```yaml
pull_request:
  branches: [staging]
  paths:
    - "src/shared/python/**"
    - ...
```

### Step 4: No changes needed to ci-standard.yml

AC3 "required" is interpreted as "workflow runs and fails on shared package changes." GitHub branch protection rules (set by humans) make jobs required — this workflow runs correctly as a conditional workflow that fails on contract violations. The `staging` branch addition makes it run for PRs targeting staging.

## Files to Modify

| `.github/workflows/cross-repo-python-integration.yml` | Modify | Expand trigger paths, add staging, improve summary |

## Edge Cases

- If downstream repo checkout fails (private repo, token scope): job gracefully skips with warning — this is correct behavior
- If downstream `tests/shared_contracts/` doesn't exist yet: job skips with informative message — acceptable
- If both paths filter + staging branch are added: workflow runs more frequently but remains fast (30 min timeout)

## Test Checkpoints

1. Verify the workflow YAML is valid (no syntax errors)
2. Verify the workflow triggers correctly for staging PRs
3. `ruff check` not applicable (YAML file, no Python)
4. No Python files modified — AC5/AC6/AC7 are N/A

## Risk Register

| Risk | Likelihood | Mitigation |
|------|-----------|------------|
| `actions/checkout@v6` version doesn't exist | Low | Pin to v4 if v6 not available |
| Expanded paths cause workflow to run too frequently | Low | Paths are still reasonably targeted |
| Downstream repos not accessible with GITHUB_TOKEN | Medium | continue-on-error already handles this |

## Rollback Boundary

The only change is to the workflow file. Rolling back = reverting to prior version. No schema changes, no API changes, no downstream impact.
