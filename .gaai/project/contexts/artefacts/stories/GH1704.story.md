# GH1704: Assessment: Pragmatic Programmer — Design by Contract maturity is strong but enforcement inconsistent

**Source:** D-sorganization/Tools#1704

## Description

## Assessment Category: Pragmatic Programmer — Design by Contract

**Severity:** Low — The DbC framework is well-designed but unevenly applied.

### Finding

**Positive:** The `contracts.py` module (634 lines) is mature and well-structured:
- Tri-state enforcement levels (OFF/WARN/ENFORCE)
- Function-call and decorator styles
- Exception hierarchy (PreconditionError, PostconditionError, InvariantError)
- Class invariant decorator and mixin
- Domain helpers (check_positive, check_temperature, check_pressure)
- 33 files use contracts across the codebase

**Gaps:**
1. `cors.py` uses `require()` from contracts for input validation — good
2. Most calculator modules in `src/shared/python/upstream_drift_tools/process_calculators/` do NOT use contracts despite being public API
3. No `ensure()` (postcondition) usage found in calculator return paths
4. The `CONTRACTS_ENABLED` module-level variable (line 79) reads `_ContractState.level` at import time and doesn't update when `set_contract_level()` is called (the `set_contract_level` function manually patches it, but the closure in `_handle_violation` reads the module-level `DBC_LEVEL` alias, which has the same issue)

### Recommendation

Add precondition checks to all public functions in `process_calculators/` that accept physical values (temperature, pressure, flow rate). The `check_temperature()` and `check_pressure()` helpers already exist.
