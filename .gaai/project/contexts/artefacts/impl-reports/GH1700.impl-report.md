`from src.shared.python.contracts import` usages with `from contracts import` (bare
import style), which resolves correctly because `src/shared/python` is on `pythonpath`

**Exceptions (2 files retain absolute import for cross-repo correctness):**

1. `tests/shared/python/test_cors.py` — imports `add_cors_middleware` from
   `src.shared.python.cors` which resolves to UpstreamDrift's `cors.py` (via sys.path).
   UpstreamDrift's module uses a relative import to its own `contracts.py`, so the
   `PreconditionError` raised is `src.shared.python.contracts.PreconditionError`. The
   test must catch that exact class → retains `from src.shared.python.contracts import`.

2. `tests/shared/python/gui_launcher/test_registry.py` — `test_auto_discover_non_list`
   imports `auto_discover_guis` from `src.shared.python.gui_launcher.registry` (UpstreamDrift).
   Same cross-repo reason → retains `from src.shared.python.contracts import` for that
   one test method only.

## Known Risks / Limitations

The 2 cross-repo test exceptions are intentional design choices, not defects. They document
a real constraint: tests that exercise UpstreamDrift modules (loaded via `src.shared.python.*`
path) must catch the class that UpstreamDrift raises. This is a known limitation of the
cross-repo monorepo symlink architecture. A future story could address this by ensuring
UpstreamDrift and Tools use the same `contracts` module object (e.g., via shared installation).
