## 1. Cargo ecosystem missing from Dependabot — implemented

**Use case:** `.github/dependabot.yml` tracked `pip` and `github-actions`
but had no `cargo` entry, even though the repo is a 6-member Cargo
workspace (`Cargo.toml`: `tools-core`, `math-primitives`, `ai_backend`,
`file_watcher`, `data-processor-core`, `swing-core`, plus the
intentionally-excluded `pendulum-core`) — 13 `Cargo.toml` manifests in
total. `rust_core/ai_backend/Cargo.toml` pins `ort = "=2.0.0-rc.10"` and
`ort-sys = "=2.0.0-rc.10"` (ONNX Runtime bindings, still pre-1.0) with a
comment noting the API moved between RCs — exactly the kind of dependency
that needs an automated nudge when a new RC or the 2.0 GA lands, instead of
a human remembering to check crates.io.

**Alternatives considered:** none — this is enabling an existing,
already-adopted tool (Dependabot already covers `pip` and
`github-actions` in this same file) for an ecosystem it was never
pointed at. No new runtime dependency, no new SDK.

**License / supply chain:** N/A — GitHub-native feature, no new code in
the dependency graph. It only opens PRs for a human/bot reviewer to merge;
nothing auto-merges.

**Maintenance / bus-factor:** N/A (not a package).

**API / stability risk:** None. Dependabot PRs for Cargo bump `Cargo.toml`
version requirements only; the existing `maturin-*` and Cargo CI gates
(`ci-standard`'s Rust lane, `.cargo-rust-quality`) validate each bump the
same way they validate a human-authored one.

**Integration cost:** Done — one block added to
`.github/dependabot.yml`, mirrors the existing `pip`/`github-actions`
entries (weekly, `open-pull-requests-limit: 10`).

**Reversible PoC / exit plan:** Delete the four added lines. No code,
schema, or lockfile touched.

integration scout should check for a ready-made pose-capture stack.

**Finding:** `src/shared/python/sidekick/lab/mocap/AGENT_HANDOFF.md`

add a vendor SDK, model weight, FreeMoCap, or SkellyCam dependency to the
MIT core."* The adapter layer

would otherwise propose (keep the model-weight dependency optional and
licensing-gated, never hard-vendored into the MIT core) is already built
and already rejected the two most obvious OSS shortcuts by name. Nothing
to add; re-confirming the existing decision rather than re-litigating it.

**Exit plan:** none needed — no new dependency proposed.

## 3. `schemdraw` (MIT, PyPI `schemdraw`) for `programmatic_pid` — reject

**Use case:** `src/shared/python/programmatic_pid/` (≈3.9k lines across
`spec_loader.py`, `streams.py`, `title_block.py`, `types.py`,
`validation.py`, plus the renderer consumed by
`src/pid_generator/ui/pyqt6/main_window.py`) is a bespoke SVG renderer for
ISA S5.1 P&ID symbology. `schemdraw` (actively maintained, MIT, pure
Python, last tagged release within the past year) is a credible
general-purpose schematic-drawing library and was the first thing worth
checking against this module.

**Alternatives already in the stack:** the existing
`programmatic_pid` package already owns title blocks, stream tables, and
ISA-specific symbol validation — domain logic `schemdraw` has no concept
of.

**Why reject:** `schemdraw`'s symbol library is electrical/logic-gate
oriented; none of the ISA S5.1 instrument-bubble or valve symbology
`programmatic_pid` implements exists upstream, so adopting it would not
remove any of the ~3.9k lines of domain logic — it would only add a second
rendering dependency alongside the PyQt6 `QGraphicsScene`/SVG path already
in `ui/pyqt6/main_window.py`, for no symbol reuse. Duplication without a
clear win; default reject per playbook.

**Exit plan:** none needed — no new dependency proposed.
