## Principle Assessment

### DRY — Concerning

Fleet operational tooling is duplicated across repositories as vendored source rather than as a shared, versioned dependency. In the reviewed week alone:

- `a4094e8ac` — "vendor stalled-merge requeue tooling from Repository_Management (#2018)": adds `scripts/automerge_guard.py` (774 lines) and `scripts/requeue_stalled_merges.py` (181 lines) plus 1,272 lines of their canonical tests, explicitly described in the commit message as "byte-identical from RM main."
- `acb4fd4c5` — "re-vendor fork_pr_runner_guard + analysis module (RM#1996)": 794 lines changed to pull in RM's updated guard and a new `fork_pr_guard_analysis.py`.
- `ad5309384` — "vendor RM-5 change fragments, freshness check, and receipt (Repository_Management#1976)".
- `863cb3fbc` — "re-sync vendored requeue tooling from Repository_Management" (a second touch of the same files within the same week).

Each of these exists solely to keep a copy in sync with its single source of truth. The failure mode this produces is not hypothetical: the fork-PR guard ran with stale logic in `Tools` until `acb4fd4c5` manually re-vendored RM's fix — a correctness gap that a version-pinned dependency would close automatically (or at least make visible as "N releases behind" instead of silent drift).

**Pathway:** Package the fork-guard / requeue / change-fragment tooling as an installable `Repository_Management` distribution (versioned, with a CHANGELOG) that `Tools`, `UpstreamDrift`, and `Gasification_Model` depend on and pin, rather than copying source trees. This is the project's own DRY rule — "duplicated logic in UpstreamDrift or Gasification_Model belongs here" — applied symmetrically: duplicated *infrastructure* logic across repos belongs in exactly one place too, with the others consuming it as a dependency.

### Orthogonality — Healthy

- `190cfeba1` ("run required checks in the merge queue") and `0b1f76482` ("drop Auto-Update PRs now that the merge queue serializes merges") remove a real coupling: previously every open PR had to rebase in reaction to every *other* PR landing on `main` to stay green. Serializing through the merge queue means a PR's CI state no longer depends on unrelated PRs' merge order.
- The four `chore(changes): collate N fragment(s)` commits this week (e.g. `1350a352e`, collating 8 fragments at once) implement the change-fragment pattern precisely as designed: individual PRs append an isolated fragment file instead of editing `SPEC.md` / `HANDOFF.md` / `DEVELOPMENT_LOG.md` directly, and a single post-merge job applies them. This removes the shared-mutable-document merge-conflict surface that used to make every doc-touching PR a potential conflict with every other one.

### Broken Windows — Healthy

Issue #5440 (test-shard hangs under the Qt GUI suite) produced three fixes landed the same day rather than being tolerated as flake:

- `2966a2115` — dropped `faulthandler_timeout` because its mid-test dump was itself crashing `tests-shared`.
- `ead6be5fc` — added explicit tab-state waits in the variation GUI execution tests.
- `aeaad3e0e` — fixed a solver panel-run test that could hang a shard on a lost Qt signal, and in doing so added `tests/rate_of_closure/_qt_waits.py`, a shared wait helper now used by multiple test files instead of a third pasted copy of wait logic.

Treating each symptom as it was found, and factoring out the shared helper on the final fix rather than copying it again, is exactly the "repair the window as soon as it's discovered" behavior the principle asks for — worth calling out as a model to repeat.

### Reversibility — Healthy

`config/license_denylist.json` (ADR-008, `d7cef753e`) and the existing `config/coverage_policy.json` keep policy data externalized and editable rather than hard-coded into the scripts that enforce them. The runtime-manifest validator (`f729eca97`) is a disciplined parity port — it reuses the existing shared fixture to prove Python/TypeScript agreement rather than inventing a new contract test, keeping the two implementations swappable without a rewrite of either.

### Good Enough Software — Healthy

No evidence of premature optimization or scope creep this week. The CAD, mocap, and runtime-manifest features reviewed are each scoped to a single sub-task with a stated "next" (e.g. iron-head CAD family explicitly defers cavity/ports/leading-edge radius to a later pass rather than gold-plating v1).

## Patterns Observed

- **Vendoring as a recurring tax.** Beyond the four commits above, the fork-PR guard has now been "re-vendored" from RM at least twice in recent history (see `docs/development/HANDOFF.md`'s "Re-vendor fork PR runner guard (RM#1996)" entry). This is a pattern, not a one-off: every RM-side improvement to shared fleet tooling currently requires a manual, byte-identical re-sync PR in every consuming repo.
- **Change-fragment discipline is being followed correctly** by the PRs reviewed this week — none of them hand-edited `SPEC.md` or `HANDOFF.md`'s shared tables directly; they either used the fragment tool or (for docs-only steward passes) stated "no SPEC.md entry required" correctly per the `SOURCE_CHANGED=false` rule.

## Improvement Pathways

1. **Centralize fleet-ops tooling behind a published dependency.** Convert `scripts/automerge_guard.py`, `scripts/requeue_stalled_merges.py`, `scripts/fork_pr_runner_guard.py`, `scripts/fork_pr_guard_analysis.py`, and the change-fragment tooling into one versioned `Repository_Management` package that `Tools` installs and pins (wheel or git-tag pin), replacing the vendored copies and their matching canonical test suites. Estimated removal: ~1,750 lines of vendored source plus ~1,650 lines of duplicated canonical tests from `Tools` alone, multiplied across every other consuming repo.
2. **Track staleness explicitly if full centralization isn't feasible soon.** At minimum, add a scheduled check that diffs the vendored files' hashes against RM's canonical copies and opens a single tracking issue when they drift, instead of discovering drift only when a guard fails to catch something it should have caught.

## Commendations

- The merge-queue migration (`190cfeba1`, `0b1f76482`) is a clean orthogonality fix: it was scoped to exactly the CI coupling it targeted, with no collateral changes to unrelated workflow logic.
- The #5440 triad is a good example of "fix forward, extract shared helper" instead of "patch and move on" — `_qt_waits.py` is the kind of DRY instinct that should be the default when a second GUI test needs the same wait logic.
- The change-fragment collation workflow is doing exactly what it was designed to do, four times in the reviewed week, with no observed hand-edit regressions to the shared docs it protects.
